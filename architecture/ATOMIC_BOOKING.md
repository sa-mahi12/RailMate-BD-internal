# Multi-passenger and multi-seat atomic booking contract


A booking request supplies trip ID, 1–4 passenger objects, 1–4 distinct seat codes, corresponding index mapping, request UUID and simulated payment success/failure. The Edge Function verifies Supabase JWT, validates user, shapes and allowed capacities, enforces body size and per-user rate limit, refuses past/inactive trips, then invokes a single service-role-only Postgres function under a transaction. The function acquires targeted seat rows in stable sorted order; verifies requested set exactly matches unbooked inventory and passengers count; creates booking, passengers and seat assignment; marks seats with booking ID atomically; returns one confirmation record. For any missing/conflicting seat, raise an error and roll back every write. On retries the same user + request UUID returns the original booking without doubling seats or charging anything; same request UUID with mismatched content must reject.

**Avoid deadlock:** Rows should be acquired in sorted seat code order and no long external API call inside SQL transaction. **Avoid spoofing:** The public client never provides an effective owner ID and never calls service-role RPC. **Avoid double purchase:** The transaction must own both booking creation and seat update. **Avoid orphan tickets:** Render tickets from confirmed booking snapshots; PDF/QR generation can occur after commit because it is a reversible display operation. **Avoid false success:** On network timeout check by request UUID before retry; do not assume non-response equals failure.

**Cancellation:** Validated owner or explicitly authorized admin only. Lock booking and assigned seat rows, transition CONFIRMED→CANCELLED, release seats that still reference this booking, set cancellation timestamp. Repeating cancellation returns the prior cancelled record; partial cancellation and refund are excluded. Cancellation must not release seats booked under any other booking ID. All writes in one DB transaction.

**Concurrency acceptance:** Two accounts booking same A1 concurrently yields one confirmed and one seat-unavailable; disjoint seat sets both succeed; two intersecting multi-seat sets never partially succeed; duplicate same request ID returns same booking; failing payment creates no booking; cancel/rebook success; interrupted network recovers by request key. Use an independent backend-level test instead of a Flutter-only mocked fixture to claim atomicity.
