# Staging SQL assertions — read-only unless explicitly marked

After a staging apply, verify RLS is enabled on every exposed table: `select relname,relrowsecurity from pg_class join pg_namespace ... where nspname='public' and relkind='r';`. Verify RPC grants with `select has_function_privilege('anon','public.book_trip_service(uuid,uuid,uuid,jsonb,text[])','EXECUTE')` (expect false) and similarly authenticated false/service_role true. Check normalized username uniqueness by concurrent insert; check trip seat unique constraint and bookings `(user_id,request_id)` unique index. Never test on production data using real customer names. Two-service calls with overlapping seat sets must yield one 409 and no partial booking. Compare booking_passengers, booking_seats and trip_seats rows before/after failure. Re-run same request UUID, ensure same booking ID and row counts unchanged. After cancellation, only that booking's seats become free. Third account SELECT on bookings/passengers must return no rows; third account booking cancellation must 403/404.

For post tables, test public SELECT vs private profile, one reaction per `(post_id,user_id)`, valid star 1–5, and image path upload constrained by user ID. For GraphQL, confirm pg_graphql extension enabled and discover current schema/introspection availability rather than hardcoding a table name that may change under inflection. For realtime, enable the relevant publication/table and prove two-client receipt. Every staging test logs exact project ref, migration id, transaction state and sanitized result; no unreviewed live apply.
