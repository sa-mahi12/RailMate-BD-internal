# Protected hosted booking function — executable design, not deployed code

Implement in `supabase/functions/book-trip/index.ts` only after schema/RPC reviewed. Use official `supabase-js` server client and Deno. Extract Bearer token from request; use a publishable-key client to call `auth.getUser(jwt)`; refuse invalid JWT. Create a distinct service-role client **only in hosted Edge Function environment** using `SUPABASE_SERVICE_ROLE_KEY`. Validate content type/size, trip ID, request UUID, 1–4 passengers and seats, pairwise distinct seat codes, and demo payment flag. Never accept owner ID from body. If mock payment=false, return a labeled failed simulation and perform no RPC. If true, invoke `book_trip_service` with verified `user.id`, trip ID, passengers, seats and request UUID. Return only the booking ID and status; fetch other details through owner-scoped RLS on the Flutter client. Convert database constraint errors to 409 conflict/400 validation without disclosing SQL internals. Return retry/unknown on network ambiguity and query idempotency UUID before repeating. No real payment provider integration, no financial identifiers.

Service-role exposure prevention: no console.log request body, no function response containing key, no plaintext service key in package, no client `--dart-define` for service role, no direct grant EXECUTE to anon/authenticated. Unit tests use fake auth + RPC client; staging integration uses two different JWTs and actual DB seat contention. An Edge Function's 200 status alone does not prove atomicity.
