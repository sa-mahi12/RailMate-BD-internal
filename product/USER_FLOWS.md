# Minimal user and error flows

Happy path: install APK → register account → real email verify → phone OTP if configured → choose source/destination/date → see seed trips → choose 2 seats → enter 2 names → review demo fare → simulated success → protected booking transaction → confirmation and demo ticket PDF → history → whole booking cancellation → seats become free. Exactly one seat per passenger, maximum four; passenger order and coach seat labels must be stable. A second account can simultaneously attempt one selected seat and see a truthful conflict.

Failure paths: same username conflict at final claim; expired email link; phone SMS provider unavailable; offline search; empty route; date in past; occupied seat; changed availability after selection; repeated pay button; unknown result after network timeout; PDF share permission denied; logout while private detail open; post upload interrupted; duplicate realtime event; missing TFLite asset; no OpenRouter key; bad key/rate limit/provider failure; blocked embedded media. Each path results in specific state, never a generic false success. Testing modes are distinct: fixture/unit, hosted integration, Android device, live external provider.

Account privacy flow: account A booking never appears to B; B cannot call cancellation for A; post/public community data is intentionally separate from private profile and passengers. BYOK flow: key stored on own device, explicit content rewrite only, remove key; never copy prompt or key to docs logs. No AI should mutate booking. Every flow is backed by the course matrix row and actual evidence.
